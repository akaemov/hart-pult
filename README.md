# Пульт HartDevelopment

Коммерческий пульт застройщика: темп продаж против плана, скорость обработки
обращений, структура остатка и стоимость целевого лида — на одном экране.

ТЗ: https://claude.ai/code/artifact/8d985ce3-bbed-4c22-af42-7c64d95dc527

## Два правила, которые проверяются в каждом ревью

1. **По любой цифре можно провалиться в список сделок**, из которых она посчитана.
2. **На каждом окне — время последнего успешного обновления.** Данные берутся
   из таблицы `SyncRun`; окно без отметки свежести не принимается.

## Окна пульта

Главный экран разбит по вопросам, которые решает застройщик, а не по сервисам:
самые важные цифры собираются из нескольких источников сразу. CPQL — это расход
из рекламных кабинетов, делённый на целевых лидов из amoCRM; в окне одного
сервиса его не посчитать. Отдельные окна по кабинетам — на вкладке «Реклама».

### Что обязано быть у каждого окна

- **Подпись источников**, из которых собрано окно.
- **Свежесть по каждому источнику отдельно.** Если хотя бы один устарел,
  устаревшим помечается всё окно: половина свежих данных плюс половина
  вчерашних даёт неверную цифру, а не почти верную.
- **Уровень достоверности** данных в окне:

  | Уровень | Что значит |
  |---|---|
  | A | машинная запись, подделать нельзя |
  | B | собственный учёт, зависит от дисциплины ввода |
  | C | оценка человека |
  | D | внешние данные, годятся только для динамики |

- **Проваливание в список сделок**, из которых посчитана цифра, с выгрузкой.

### Обзор

Открывается первым. Сначала отвечает, идём ли мы по плану, затем показывает,
где теряем. Расход и реклама вынесены на второй уровень: это объяснение, а не
заголовок. На экране не больше десяти показателей, остальное уходит в детализацию.

**Верхняя строка**, каждая цифра — с дельтой к предыдущему равному периоду:
продано (шт.) против плана · выполнение квартального плана · средняя цена м² ·
остаток · медиана времени первого контакта · необработанные обращения
прямо сейчас · расход · CPQL.

Под строкой — четыре окна, свёрнутые версии вкладок ниже: темп продаж,
обработка обращений, что не продаётся, каналы.

### Продажи

| Окно | Что показывает | Источники | Ур. |
|---|---|---|---|
| Темп продаж против плана | Факт и план по месяцам и накопительно с начала квартала, в штуках и метрах | учёт остатков, финмодель | B |
| Цена метра | Средняя цена по состоявшимся сделкам (не по прайсу) против плановой | учёт остатков | B |
| Что не продаётся | Остаток по типам квартир и этажности, дни в экспозиции, лоты без показов за 60 дней | учёт остатков, amoCRM | B |
| Брони и договоры | Когортой по месяцу, в котором пришёл лид: цикл покупки длится месяцы | amoCRM, учёт остатков | B |

### Обработка

Самые достоверные данные пульта: время ставит система, а не человек.

**Время здесь рабочее — с 9:00 до 20:00 по месту объекта.** Календарная разница
размывает картину: заявка в 21:40 с ответом в 09:10 выглядит как одиннадцать
часов молчания, хотя менеджер ответил за десять минут работы. Вечер и ночь
выкидываются из расчёта, поэтому медиана говорит о работе отдела, а не о том,
что ночью никто не звонит. Календарное время остаётся в подсказке при наведении
и отдельной колонкой в выгрузке CSV.

Выходные не исключаются: в недвижимости офис продаж работает и в субботу.
По той же шкале считается и порог необработанного обращения — два рабочих часа,
а не два календарных.

| Окно | Что показывает | Источники | Ур. |
|---|---|---|---|
| Необработанные обращения | Сделки без исходящего контакта дольше 2 часов. Счётчик текущего состояния, обновляется каждые несколько минут | amoCRM | A |
| Первый контакт | Медиана времени до первого звонка, доля ответов дольше 30 минут, по менеджерам | amoCRM + телефония | A |
| Дыры в графике | Время реакции по часам и дням недели | amoCRM + телефония | A |
| Конверсия по менеджерам | От обращения до показа и брони | amoCRM | C |

### Реклама

Здесь каждый кабинет — отдельное окно, чтобы не открывать их по очереди.

| Окно | Что показывает | Источники | Ур. |
|---|---|---|---|
| Каналы | Расход, лиды, целевые лиды и CPQL по каналам. Строка «не определён» видна всегда. Различия меньше 15% не выделяются: атрибуция — модель, а не факт | кабинеты, amoCRM | A / C |
| Яндекс.Директ | Расход, показы, клики, CTR, цена клика; кампании с расходом и без целевых лидов | Директ, amoCRM | A |
| VK Ads | То же для VK | VK Ads, amoCRM | A |
| Яндекс.Метрика | Визиты, отказы и достижения целей по источникам трафика | Метрика | A |

### Спрос

| Окно | Что показывает | Источники | Ур. |

| Индекс спроса | Динамика групп запросов (по объектам, районам, типам жилья) к базовой неделе. Абсолютные числа не показываются | Вордстат | D |

| Окно | Что показывает | Состояние |

### Режим показа

Учётная запись с ролью «Просмотр» видит все окна, но без контактов
покупателей, ставок и настроек. Её можно открыть на встрече или отдать
подрядчику, не выдавая доступ к кабинетам и CRM.

## Запуск локально

```
npm run pult
```

Поднимает локальную базу, если она не запущена, ждёт её, стартует сервис на
http://localhost:3050 и открывает браузер, когда страница готова отвечать.
Остановить — Ctrl+C. Повторный запуск не плодит второй процесс, а говорит,
что пульт уже работает.

Отдельные шаги, если что-то пошло не так:

```
npm run db:dev     # только база (локальный Postgres из prisma dev)
npm run dev        # только сервис, база должна быть уже поднята
npm run user:add -- --email owner@hart.local --reset   # новый пароль
```

## Диагностика amoCRM

Первый шаг проекта: до разработки окон нужно понять, в каком состоянии данные.

```
npm run diagnose -- --days 90
```

Скрипт только читает amoCRM — ничего не пишет ни в CRM, ни в базу — и сохраняет
отчёт в `reports/`. Он отвечает на три вопроса:

1. **Доходит ли до CRM источник обращения.** Ищет поля сделки с UTM и источником
   и считает их заполненность. Пустой источник у половины сделок означает, что
   CPL по каналам считать не из чего.
2. **Звонят ли менеджеры через телефонию.** Читает примечания-звонки и на сделках,
   и на контактах. Ноль звонков означает, что времени первого контакта в природе
   не существует и блок «Обработка» не построить — это блокер фазы 1.
3. **Как быстро отвечают.** Медиана времени до первого исходящего звонка, доля
   ответов дольше 30 минут, открытые сделки без звонка дольше двух часов,
   разрез по ответственным.

Нужен долгосрочный токен приватной интеграции в `.env` (`AMO_SUBDOMAIN`,
`AMO_LONG_LIVED_TOKEN`). Он берётся в amoCRM: Настройки → Интеграции →
ваша интеграция → Ключи и доступы.

## Сбор данных

```
npm run sync -- amocrm --days 120
```

Прогон идемпотентен: те же данные можно собрать повторно, всё перезапишется.
Инкрементального сбора нет намеренно — статусы сделок и звонки меняются задним
числом, а объём за квартал измеряется тысячами строк. Каждый прогон оставляет
строку в `SyncRun`, каждый ответ API — в `RawPayload`; на них держится отметка
свежести на окнах и пересчёт задним числом, когда поменяется формула.

На сервере сбор будет запускаться systemd-таймером. Частый опрос нужен только
amoCRM: счётчик необработанных обращений — состояние на сейчас, на него
реагируют в течение дня.

### Автообновление на Mac

Сбор запускается сам, двумя агентами launchd:

| Агент | Когда | Глубина |
|---|---|---|
| `ru.hartpult.sync.recent` | каждые 15 минут | 7 дней |
| `ru.hartpult.sync.full` | ежедневно в 04:30 | 180 дней |

Частый сбор мелкий и занимает около 15 секунд — этого хватает, чтобы счётчик
необработанных обращений не отставал больше чем на четверть часа. Ночной
проходит по всей истории: статусы старых сделок меняются задним числом, и
частый сбор их не видит, потому что смотрит только свежее окно.

Агенты работают, пока Mac включён; пропущенные за время сна запуски launchd
не навёрстывает. Если база не поднята, сбор пропускается с записью в лог,
а не падает с ошибкой.

```
tail -f logs/sync.log                                  # что происходит
launchctl list | grep hartpult                         # агенты на месте
launchctl start ru.hartpult.sync.recent                # запустить сейчас
launchctl unload ~/Library/LaunchAgents/ru.hartpult.sync.recent.plist   # выключить
```

На сервере этих агентов не будет — там ту же роль выполнят systemd-таймеры.

## Миграции на локальной базе

`prisma dev` отдаёт одно и то же хранилище под любым именем базы, поэтому
теневая база, которая нужна `prisma migrate dev`, там невозможна: она приезжает
с уже созданными таблицами, и миграция падает на `type "Role" already exists`.
Миграции здесь создаются сравнением схемы с живой базой:

```
dir="prisma/migrations/$(date +%Y%m%d%H%M%S)_имя_миграции"
mkdir -p "$dir"
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script > "$dir/migration.sql"
npx prisma db execute --file "$dir/migration.sql"
npx prisma migrate resolve --applied "$(basename "$dir")"
```

На сервере с обычным PostgreSQL ничего этого не нужно: там работает
`prisma migrate deploy`.

## Устройство

| Где | Что |
|---|---|
| `lib/auth/` | Вход: scrypt-хеши, сессии в базе, блокировка после 5 неудачных попыток |
| `lib/auth/dal.ts` | Единственное место проверки доступа — вызывается каждой страницей |
| `proxy.ts` | Только быстрый редирект без cookie; доступ не проверяет |
| `lib/sync/` | Реестр источников, прогоны сбора, расчёт свежести данных |
| `prisma/schema.prisma` | `RawPayload` хранит ответы API целиком — для пересчёта и проваливания |
| `app/api/health` | Проверка для мониторинга: процесс жив, база отвечает |

Сбор данных не выполняется при открытии страницы: сборщики запускаются по
расписанию и пишут в базу, интерфейс читает только её.

Время хранится в UTC, показывается по Москве (`lib/format.ts`).
